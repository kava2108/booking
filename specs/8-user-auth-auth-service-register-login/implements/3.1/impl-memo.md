# 実装判断メモ: 8-user-auth-auth-service-register-login / 3.1

## 採用したアプローチ

- **JWT は internal/auth に集約**（HS256 のみ受理、exp 必須、issuer・sub(UUID)・role を検証、鍵 32 bytes 以上）。service が発行し middleware が検証するので実装が 1 箇所。
- **リフレッシュトークンは opaque**（32 bytes 乱数の base64url。DB には SHA-256 の 16 進 64 文字のみ）。
- **未登録ログインでもダミー bcrypt 比較**: 応答時間でユーザーの存在を推測させない。テストは cost 10 で実測（比較が走らなければ ~0ms）。
- **パスワード検証は rune 数 ≥ 12 かつ ≤ 72 bytes**: bcrypt の 72 bytes 上限を超える入力を明示的に拒否（無視されて先頭 72 bytes だけ検証される事故を防ぐ）。
- **重複判定は一意制約**（事前の存在確認 → 登録の競合を避ける）。
- **メールは非同期（注入可能）**: 失敗は error ログのみで登録・リセットを失敗させない。宛先・トークンはログに出さない。
- **SMTP**: 宛先に改行/複数アドレスを含むと拒否（ヘッダーインジェクション）。件名 RFC2047、本文 base64。
- **JWT_REFRESH_SECRET は未使用**: リフレッシュは opaque トークンのため鍵が不要。config の必須項目として残っているが使っていない（TODO）。

## 検討した代替案

| 代替案 | 不採用の理由 |
|---|---|
| リフレッシュトークンも JWT | 失効・ローテーションは DB 管理が必要で、JWT にする利点が無い |
| 登録時に先に FindByEmail で重複確認 | 競合で二重登録が起き得る |
| echo-jwt を使う | 検証ロジック（alg 固定・role 検証・Identity 変換）を自前で一本化したいため #10 で自前ミドルウェアにした |

## 既存コードへの影響

新規のみ。config の JWT_SECRET は 32 bytes 以上が必要（起動時に検証）。

## 変更 (2026-10-10): ログイン制限をアカウント単位に変更

- **要件 REQ-002-AC-3 を変更**: 「同一 IP から 5 回」→「同一アカウントで連続 5 回失敗で 15 分ロック」。共有 Wi-Fi（病院の待合室など）の患者を巻き込む問題の解消が目的。
- **実装**: service の `AttemptGuard`（メモリ実装 `MemoryGuard`）。キーは正規化したメール。連続失敗のみ数え、成功と本人確認済みのパスワード再設定で解除。ロック中は正しいパスワードでも拒否し DB にも触れない。未登録メールも同じ回数でロック（存在の推測防止）。インフラ障害は数えない。キー数に上限（既定 10 万）。
- **IP 単位は緩い天井に格下げ**: `RATE_LIMIT_LOGIN_IP_MAX`（既定 100 / 15 分、全アカウントをまたぐ試行）。パスワードスプレー対策。登録・リセットは `RATE_LIMIT_SENSITIVE_MAX`（既定 20）。
- **リセット申請を宛先単位で制限**: 1 時間に 3 通まで（メール爆撃対策）。超過しても応答は同じ。
- **429 に Retry-After**（残り秒数）。
- **新しいリスク**: 他人のアカウントを意図的にロックできる（攻撃者が誤ったパスワードを 5 回送る）。緩和: 15 分で自動解除／パスワード再設定で即解除／Retry-After で利用者に通知。さらに強くするなら (account, IP) の組での制限や CAPTCHA を検討。
- **制約**: ロック状態はプロセスのメモリ上。再起動で消え、複数台では共有されない。複数台構成にする前に共有ストア実装（Redis 等）へ差し替える（`AttemptGuard` interface 越しなので差し替え可能）。
