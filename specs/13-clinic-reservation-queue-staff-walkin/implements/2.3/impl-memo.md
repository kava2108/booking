# 実装判断メモ: 13-clinic-reservation-queue-staff-walkin / 2.3

## 採用したアプローチ

- **診療科の行ロック（SELECT … FOR UPDATE）で受付を直列化**: 当日受付の定員判定と受付番号の採番を同一診療科で直列化し、並行でも定員超過・番号重複が起きない（15 並行 → 5 件、番号 1〜5）。一意制約違反（`queue_entries_ticket_key`）は最終防壁として Tx ごと再試行。
- **sort_time = max(予約時刻, 来院受付時刻)**（予約）/ 受付時刻（当日受付）。遅刻者が先着の当日患者を追い越さない規則を service の 1 箇所に集約。
- **状態遷移は SQL の `WHERE status = 現在値`**。0 行のとき項目の有無を確認して 404 / 409 を分ける。service にルールを二重定義しない。
- **完了で予約も completed**（同一 Tx）。これを怠ると予約が booked のまま残り、同時刻の予約チェックを汚染する。
- **監査ログは「個人情報を返すリクエストだけ」記録**: パラメータ検証を監査の前に置いた（当初は不正リクエストも記録していた → テストで発見）。監査に失敗したら 500 でデータを返さない（フェイルクローズ）。
- **システム管理者は staff API 不可**（患者の氏名・症状メモを見られない最小権限）。クリニック管理者はスタッフ操作も可。
- 来院受付の `{id}` は予約 ID、その他は待機列 ID（OpenAPI の説明にも記載すべき → TODO）。

## 検討した代替案

| 代替案 | 不採用の理由 |
|---|---|
| アプリ側の Mutex で直列化 | 複数インスタンスで破綻する |
| 採番を DB シーケンスに | 日次・診療科別のリセットが必要 |
| 遷移を SELECT → UPDATE の 2 段階に | 競合で二重遷移 |
