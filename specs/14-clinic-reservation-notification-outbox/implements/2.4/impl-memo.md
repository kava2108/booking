# 実装判断メモ: 14-clinic-reservation-notification-outbox / 2.4

## 採用したアプローチ

- **重複防止は DB の部分ユニークインデックス（000009）**: `appointment_reminder` は `payload->>'appointment_id'`、`queue_near` は `payload->>'queue_entry_id'` で一意。`INSERT … ON CONFLICT DO NOTHING` の更新件数で「新規登録か」を判断。登録側が並行（複数スケジューラー）でも 1 件。アプリ側の「あれば登録しない」チェックだけでは競合窓が残るため。確認/取消/変更の通知は同じ予約に複数あり得るので対象外。
- **ワーカーは at-least-once**: リース方式で取得（長い Tx を持たない）。送信後・状態更新前にクラッシュすると再送され得るが、通知は多重送信より欠落が害が大きいため許容。
- **バックオフは `base × 2^(attempts-1)`（1,2,4,8 分、上限 1 時間）、5 回目の失敗で failed**。再試行しても無駄なもの（宛先不明・未知種別・壊れた payload）は即 failed。
- **本文は既知の型にデコードして必要項目だけ描画**: payload に症状・診断・メールが紛れても本文に出ない（テストで注入して確認）。時刻は常に JST 表示。
- **ログは通知 ID と種別のみ**（宛先・氏名・本文・payload を出さない。テストで検証）。
- **リマインドは前日 18:00(JST) 以降、翌日の予約に 1 回**。18:00 以降に翌日の予約を取った人には次の実行（1 分以内）で送る。
- **SMTP 未設定ならワーカーを起動しない**: 通知は pending のまま残り、設定後に送られる（Noop で sent にして握りつぶさない）。
- **通知手段は NotificationSender interface**。SMS / LINE は実装を差し替えるだけ。

## 検討した代替案

| 代替案 | 不採用の理由 |
|---|---|
| 登録前に SELECT で存在確認 | 並行で二重登録の競合窓が残る |
| Noop で sent にする | 未送信なのに送信済みになり、設定後も送られない |
| 通知テーブルに dedupe_key 列を追加 | 既存列(payload)から導出できるためインデックスのみで足りる |

## 既存コードへの影響

notifications テーブルにインデックス追加のみ（#4 のスキーマ変更なし）。#12 の確認/取消/変更の通知がここで初めて送信される。
