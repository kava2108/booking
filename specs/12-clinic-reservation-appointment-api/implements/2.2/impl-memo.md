# 実装判断メモ: 12-clinic-reservation-appointment-api / 2.2

## 採用したアプローチ

- **検証 → 重複チェック → 枠確保 → 予約作成 → 通知登録を 1 Tx** に。どこかで失敗すれば全体が巻き戻る（FK 違反を起こすテストで枠の確保が戻ることを確認）。
- **満席の判定は ReserveSlot の条件付き UPDATE に一本化**（事前に capacity を読んで判断しない）。20 並行でも成功は 1 件。
- **重複予約は二段構え**: 事前チェック（同時刻の別枠も含む）+ DB の部分ユニーク制約（同一枠）。制約名で意味を判別（`appointments_no_key` → 番号を変えて再試行、`appointments_active_patient_slot_key` → 重複）。
- **予約番号の衝突は Tx ごと再試行**（Postgres は一意制約違反で Tx が中断するため、Tx 内の再試行はできない）。
- **取消と変更は同じ期限規則**: 開始のキャンセル期限分前より前のみ。期限ちょうどは不可（境界をテストで固定）。変更は元の予約の開始時刻を基準にする。
- **同時刻の別医師への変更**は、自分自身の予約を重複とみなさない。
- **通知 payload は AppointmentNotice 型**で、症状メモのフィールドを持たない（型でも保証）。メール送信はせずアウトボックス登録のみ（#14 が送信）。
- **他人の予約・取消済み・不正な UUID はすべて 404**。存在の有無を漏らさない。
- 個人情報を含む応答は `Cache-Control: no-store`。

## 検討した代替案

| 代替案 | 不採用の理由 |
|---|---|
| 予約番号に DB シーケンス | 日付ごとのリセット・桁数の扱いが面倒。ランダム + 再試行で十分 |
| 事前に枠の空きを読んで判断 | 競合で定員超過が起き得る |
| 通知を Tx の外で登録 | 予約だけ成功して通知が欠落し得る |
